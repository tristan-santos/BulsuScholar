# REVISION 1 — RULE-BASED DECISION TREE FLOWCHART

## Objective

Determine precisely how the BulSUScholar scholarship recommendation algorithm works so that we can create a **Decision Tree Flowchart** representing the actual system logic.

Do not create a generic Decision Tree.

### Questions to investigate

**A. Implementation and inputs**

1. Where is the scholarship recommendation algorithm implemented? Identify its exact functions, files, and entry points.
2. Is the algorithm genuinely a rule-based decision process, a machine-learning Decision Tree, a combination of filtering and weighted ranking, or something else?
3. What student attributes are retrieved and used?
4. What scholarship attributes, eligibility requirements, and restrictions are evaluated?
5. Where do the inputs originate: student profiles, scholarship records, grantor policies, academic records, or other sources?

**B. Actual decision sequence**

6. What is the first decision performed by the recommendation function?
7. What is the complete order of conditional checks?
8. For every decision, provide the exact condition evaluated.
9. What happens when each condition evaluates to TRUE?
10. What happens when each condition evaluates to FALSE?
11. Which conditions exclude a scholarship from recommendation?
12. Which conditions allow a scholarship to proceed?
13. How does the algorithm handle missing, incomplete, invalid, or unavailable student information?
14. How are scholarship-specific requirements and fallback values determined?
15. Are scholarship availability, application status, academic grades, existing scholarship commitments, and other restrictions evaluated? Specify which ones are actually checked at recommendation time and which belong to separate workflows.

**C. Recommendation output**

16. What happens after a scholarship passes all relevant eligibility checks?
17. Is weighted scoring executed after eligibility filtering? If so, what fields and calculations does it use?
18. How are qualifying scholarships ranked?
19. Are there special cases that affect the final displayed ordering?
20. What information is returned to the frontend?
21. Does the recommendation process automatically approve applications, or is approval handled separately?

**1. Verified algorithm description**

**3. Flowchart-ready node sequence**

- Start and End
- Input/Output

- YES/NO paths

Include all necessary branches but avoid internal implementation details unrelated to the main decision process.

**4. Algorithm evidence**

Identify the relevant source-code snippets, including exact file paths and line ranges. Explain which portion of the Decision Tree each snippet demonstrates.

**5. Important clarifications**

# REVISION 2 — STUDENT-RECORD VALIDATION, DUPLICATE DETECTION, AND DUPLICATION PREVENTION

## Objective

Identify the actual system processes for student-record validation, duplicate-record detection, and prevention of conflicting scholarship assignments.

We will create a **Process Flowchart**, not an algorithm flowchart.

### Critical flowchart requirement

**Do not place detailed algorithm calculations inside the main process flowchart.**

Instead, show the business process as the main flow and connect each relevant process to a separate algorithm-reference box.

For example:

Main process: "Compare Student Records"

Separate connected reference: "Weighted Record Linkage / Levenshtein Similarity"

The connection should indicate that the process uses the algorithm, without displaying its internal calculation.

Only use this example if it matches the implementation.

### Questions to investigate

**A. Student-record validation**

1. What system actions initiate student-record validation?
2. How are Certificates of Registration (COR) and Reports of Grades (ROG) uploaded and processed?
3. Which functions extract information from these documents?
4. What student and academic fields are extracted?
5. What information is checked against the student's existing profile?
6. What exact validation rules apply to COR documents?
7. What exact validation rules apply to ROG documents?
8. What happens when a document passes validation?
9. What happens when it fails?
10. Are validation rules different for registration, document replacement, application submission, renewal, or other workflows?

**B. Duplicate detection**

11. Which actions initiate duplicate-record checking?
12. What records are compared?
13. Which student attributes are checked for exact matches?
14. Which fields are compared using similarity matching?
15. Which algorithms are actually implemented?
16. Does the system use Levenshtein Distance, Record Linkage, weighted comparison, or other techniques? Identify the exact role of each.
17. What are the actual thresholds and weights, where configured?
18. How are possible duplicate matches classified?
19. What happens when a potential duplicate is identified?
20. Is the student automatically rejected, blocked, flagged, grouped, or forwarded for review? Specify by workflow.
21. What happens when no potential duplicate is identified?
22. Which records can authorized administrators review or resolve?

**C. Scholarship duplication prevention**

23. How does the system check for existing scholarship assignments or commitments?
24. Does it distinguish between pending applications, approved awards, active scholarships, inactive records, completed scholarships, and previous academic cycles?
25. Which conditions constitute an actual scholarship conflict?
26. What actions are prevented when a confirmed conflict is found?
27. Can authorized personnel override, review, or resolve conflicts? Under which exact conditions?
28. How are imported scholarship rosters included in checking?
29. Are external records obtained through manual entry, uploaded rosters, or live integrations?
30. What happens when an external scholarship provider's information has not been recorded in the system?

**D. Workflow and algorithm separation**

31. Identify every distinct validation workflow relevant to this revision.
32. For each workflow, where does it begin and end?
33. Which steps are user interactions, backend processes, or database operations?
34. Which processes invoke specific algorithms?
35. What are the actual decision branches and error paths?
36. Which validation outcomes are returned to the frontend?
37. Which processes must remain separate to avoid inaccurately representing the implementation?

**1. Verified workflow inventory**

Provide a table:

|---|---|---|---|---|---|

**2. Process flowchart mapping**

**3. Algorithm-reference mapping**

**4. Verified source-code evidence**

Provide the functions and relevant source-code excerpts demonstrating document validation, identity comparison, duplicate handling, and scholarship-conflict prevention.
